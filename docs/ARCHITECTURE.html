Arquitetura do War POC

Jogo de estratégia isométrico com construção de base e tower defense, em C++20 + raylib 5.5. Este documento descreve como o código em src/ está organizado, como a informação circula num frame e mostra, passo a passo, uma funcionalidade real (colocar um prédio) atravessando todas as camadas.

1. Visão geral

O projeto segue MVC desacoplado por um event bus. As três camadas nunca se chamam diretamente:

  • Controller src/controller/: lê teclado e mouse da raylib e publica comandos (...Requested).
  • Model src/model/: dono do estado do jogo, organizado em ECS. Reage a comandos, aplica as regras e publica notificações (...Changed, ...Placed, ...Spawned). Não chama raylib e não conhece pixels.
  • View src/view/: guarda uma cópia local do estado recebido por evento e desenha com raylib. É dona da câmera e da projeção isométrica.
  • Core src/core/: o EventBus, a lista de eventos (Events.hpp) e a raiz de composição (Game).

2. Camadas e event bus

O EventBus

Um mapa type_index → vector<handler>. Cada tipo de evento é uma struct de dados em events::. O publish é síncrono: quando ele retorna, todos os inscritos já reagiram. A lista é copiada antes de despachar, então um handler pode se inscrever durante um evento.

src/core/EventBus.hpp
template <typename Event>
void subscribe(Handler<Event> handler) {
    if (!handler) { return; }
    handlers_[std::type_index(typeid(Event))].emplace_back(
        [handler = std::move(handler)](const void* event) {
            handler(*static_cast<const Event*>(event));
        });
}

template <typename Event>
void publish(const Event& event) const {
    const auto it = handlers_.find(std::type_index(typeid(Event)));
    if (it == handlers_.end()) { return; }
    const auto handlers = it->second; // cópia: permite subscribe durante o dispatch
    for (const auto& handler : handlers) { handler(&event); }
}

3. Raiz de composição e loop de frame

core::Game cria todas as peças e roda o loop. A ordem de declaração dos membros define a ordem de construção (e a destruição na ordem inversa):

src/core/Game.hpp
// o bus vive mais que quem se inscreveu nele;
// a janela vive mais que quem usa o contexto GL
std::unique_ptr<EventBus>                    bus_;
std::unique_ptr<view::Window>                window_;
std::unique_ptr<model::GameModel>            model_;
std::unique_ptr<view::Renderer>              renderer_;
std::unique_ptr<controller::InputController> controller_;
src/core/Game.cpp
Game::Game() /* ...make_unique na ordem acima... */ {
    bus_->subscribe<events::QuitRequested>(
        [this](auto&) { running_ = false; });
    model_->initialize(); // só depois de todos inscritos
}

void Game::run() {
    while (running_) {
        controller_->update();
        if (!running_) { return; }
        model_->update(GetFrameTime());
        renderer_->render();
    }
}

5. Model e ECS

GameModel controla cena e menu e roteia os comandos da partida para os sistemas, sempre com o guard inMatch(). O estado da partida mora no ecs::Registry world_: entidade = ID (Entity), componente = struct de dados puros, sistema = classe com a lógica.

Entidade (exemplo)Componentes
Centro de ComandoBuilding{type}, Owner{player}, Footprint{origin, size}
MuroBuilding, Owner, Footprint (size 1)
UnidadeUnit{type, baseCount, size}, Owner, Health, Combat, Position{x, y}, Mover{speed, path...}

A API do Registry é pequena: create, destroy, emplace<C>, tryGet<C>, has<C>, remove<C>, each<C>, clear. Cada tipo de componente tem seu ComponentPool<C>, criado na primeira vez que é usado.

Owner está em toda entidade de jogo: nada assume um único jogador.

6. View e projeção isométrica

O Model só conhece GridPos{x, y} inteiros (tiles) ou posições contínuas em tiles (Position das unidades). A conversão para pixels fica em src/view/IsoProjection.hpp, que a View usa para desenhar e o Controller usa para o picking do mouse.

src/view/IsoProjection.hpp
constexpr float kTileWidth = 64, kTileHeight = 32;

// canto de cima do tile, em pixels de mundo
Vector2 gridToWorld(float gx, float gy) {
    return { (gx - gy) * kHalfWidth,
             (gx + gy) * kHalfHeight };
}

GridPos worldToGrid(Vector2 w) {
    const float u = w.x / kHalfWidth;
    const float v = w.y / kHalfHeight;
    return { floor((v + u) / 2), floor((v - u) / 2) };
}

// tela → mundo (Camera2D) → grid
GridPos screenToGrid(Vector2 screen, const Camera2D& cam);

A câmera (target, zoom) pertence à WorldView. Toda mudança dela publica CameraChanged, e o PlayingInputController monta o mesmo Camera2D para converter o mouse. A geometria de UI usada nos dois lados (hit-test) fica nos headers *Layout.hpp da View.

7. Exemplo completo: colocar um prédio

Funcionalidade real do jogo: com um prédio selecionado na barra de construção, o jogador move o mouse (aparece um preview verde ou vermelho) e clica para colocar. Tudo abaixo acontece dentro de controller_->update(), porque o bus é síncrono.

Passo 1: Controller converte o mouse e publica comandos

src/controller/PlayingInputController.cpp
void PlayingInputController::handleMapMouse(Vector2 mouse, const Camera2D& camera) {
    const model::GridPos tile = view::iso::screenToGrid(mouse, camera); // pixels → tile
    const bool tileChanged = lastTile_ != tile;
    publishCursor(tile);                       // BuildCursorMoved, só se o tile mudou
    // ...
    if (!hasBuildSelection_) { return; }    // cópia local vinda de BuildBarChanged
    if (pressed || (placing_ && tileChanged)) { // arrastar "pinta" muros
        bus_.publish(events::BuildPlaceRequested{localPlayerId_, tile});
    }
}

Passo 2: GameModel roteia para o sistema certo

src/model/GameModel.cpp
bus_.subscribe<events::BuildPlaceRequested>([this](const events::BuildPlaceRequested& e) {
    if (inMatch()) {                       // comandos fora da partida são ignorados
        buildings_->place(e.player, e.tile);
    }
});

Passo 3: o sistema aplica a regra, escreve no ECS e notifica

src/model/BuildingSystem.cpp
void BuildingSystem::place(PlayerId player, GridPos anchor) {
    auto& builder = builders_[player];
    if (!builder.selected) { return; }

    const BuildingType type = *builder.selected;
    const int size = buildingSpec(type).size;
    const GridPos origin = footprintOrigin(anchor, size); // cursor = centro do footprint
    if (!canPlace(player, type, origin)) { return; }

    const ecs::Entity entity = world_.create();
    world_.emplace<components::Building>(entity, type);
    world_.emplace<components::Owner>(entity, player);
    world_.emplace<components::Footprint>(entity, origin, size);
    // ...marca occupied_, registra o Centro de Comando...

    bus_.publish(events::BuildingPlaced{entity, player, type, origin, size});
    if (!isUnlocked(player, type)) { builder.selected.reset(); }
    publishBar(player);
    publishPreview(player);
}

Passo 4: a View guarda a cópia e desenha no render

src/view/WorldView.cpp
bus_.subscribe<events::BuildingPlaced>([this](const auto& e) { onBuildingPlaced(e); });

void WorldView::onBuildingPlaced(const events::BuildingPlaced& event) {
    const BuildingVisual visual{event.entity, event.type, event.origin, event.size};
    const int key = depthKey(visual.origin, visual.size);  // mantém ordenado de trás pra frente
    const auto it = std::upper_bound(buildings_.begin(), buildings_.end(), key, /*...*/);
    buildings_.insert(it, visual);
}

void WorldView::draw() const {          // chamado por Renderer::render()
    BeginMode2D(camera());
    drawGrid(cam); drawSelectedBuilding(); drawObjects(); drawHealthBars(); drawPreview();
    EndMode2D();
    drawSelectionBox();
}
Repare: o BuildingSystem não sabe que existe uma WorldView, e a WorldView nunca lê o Registry. Outro jogador (no futuro, via rede) poderia publicar o mesmo BuildPlaceRequested com outro PlayerId, e o fluxo seria idêntico.

8. Receita para uma feature nova

  1. Regra primeiro. Veja docs/GAME_DESIGN.md. Se a regra estiver TBD, pergunte antes de implementar. Depois de definida, registre lá.
  2. Eventos. Em src/core/Events.hpp, crie o comando (XyzRequested, com PlayerId) e a notificação (XyzChanged ou equivalente). Só dados, sem lógica.
  3. Componentes. Se o estado for por entidade, crie structs em src/model/components/. Nada de Texture2D: assets são referenciados por ID.
  4. Sistema. Crie ou estenda uma classe em src/model/ que recebe EventBus& e Registry&, valida com guard clauses, muda o ECS e publica a notificação.
  5. Roteamento. Em GameModel, inscreva o comando com o guard inMatch() e delegue ao sistema. Se o sistema for novo, declare o unique_ptr depois de world_ e das dependências dele, e chame reset() em resetWorld().
  6. Controller. Leia o input e publique o comando. Se precisar de hit-test de UI, coloque a geometria num src/view/*Layout.hpp compartilhado.
  7. View. Inscreva-se em LocalPlayerChanged e na notificação, guarde uma cópia local filtrada pelo id recebido, limpe-a em WorldReset e desenhe em draw() const.
  8. Build. cmake --build --preset default sem nenhum warning. Arquivos novos em src/ entram sozinhos pelo GLOB_RECURSE.

Esqueleto genérico (nomes ilustrativos):

// core/Events.hpp
struct XyzRequested { model::PlayerId player; model::GridPos tile; };
struct XyzChanged   { model::PlayerId player; /* estado que a View precisa */ };

// model/GameModel.cpp
bus_.subscribe<events::XyzRequested>([this](const events::XyzRequested& e) {
    if (inMatch()) { xyz_->apply(e.player, e.tile); }
});

// model/XyzSystem.cpp
void XyzSystem::apply(PlayerId player, GridPos tile) {
    if (!isAllowed(player, tile)) { return; }     // guard clause
    // ...muda world_...
    bus_.publish(events::XyzChanged{player /*, ...*/});
}

// view/XyzView.cpp
bus.subscribe<events::XyzChanged>([this](const events::XyzChanged& e) {
    if (e.player == localPlayerId_) { state_ = e; }
});
bus.subscribe<events::WorldReset>([this](const auto&) { state_ = {}; });

9. Regras e armadilhas

RegraPor quê
Model, View e Controller só se falam pelo busDesacoplamento e um único ponto de entrada para comandos, o que facilita colocar a rede depois.
Model sem raylib e sem pixelsA lógica fica testável e determinística. A projeção iso é detalhe de apresentação.
Eventos de gameplay levam PlayerId; componentes têm OwnerNão amarrar o jogo a um jogador local, por causa do multiplayer planejado.
model_->initialize() depois de todos se inscreveremSenão o estado inicial (SceneChanged, MenuStateChanged) é publicado sem ninguém ouvindo.
Ordem dos membros em Game e GameModelHandlers capturam this e sistemas guardam referências. Quem é referenciado precisa ser declarado antes.
unique_ptr por padrão; RAII para recursos raylibSem new/delete e sem vazamento de Texture2D/Sound.
Até 500 linhas por arquivo; guard clausesLegibilidade. Divida antes de chegar ao limite.
Cuidado com reentrância: como o bus é síncrono, publicar um evento dentro de um handler dispara outros handlers na hora. Evite ciclos (A publica B, que publica A) e não presuma que o estado de outro inscrito já foi atualizado, a não ser que você controle a ordem.
ESC não fecha o jogo (SetExitKey(KEY_NULL)). Para sair, publique events::QuitRequested. Na partida, ESC cancela a construção, depois limpa a seleção e, por fim, volta ao menu.
